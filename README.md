# 求职岗位 RAG 问答系统

> 用 **FastAPI + BM25/向量混合检索 + 本地大模型** 做的检索增强生成（RAG）应用。
> 语料是我自己抓取整理的 74 个招聘岗位。
>
> 这个项目最有意思的地方不是"我用上了 RAG"，而是：
> **我最初写的纯向量检索实测是坏的，我通过对比实验发现了原因并换掉了方案。**
> 细节见下面的 [一段踩坑记录](#踩坑记录本项目最有价值的部分)。

---

## 它解决什么问题

找工作时要反复翻几十个岗位，判断"哪些要 RAG 经验""哪些适合我"全靠人眼扫。
所以我把它做成一个能问的系统：

```
问：长沙有哪些 AI 应用开发的岗位？
答：[1] 远程 全栈AI应用开发工程师（助梦空间 / 长沙·天心区·解放西路）
    [2] ai应用开发工程师（长沙四季养生生物科技 / 长沙·岳麓区·望城坡）
    [3] AI Agent 应用开发工程师（瓦特曼智能 / 长沙·长沙县·泉塘）
    [4] AI应用开发实习生（上海科锐福克斯 / 长沙·岳麓区·麓谷）

问：哪些岗位提到了 Python？
答：[1] ai应用研发工程师（卫宁健康 / 180-220元/天）
    [2] AI Agent 应用开发工程师（瓦特曼智能 / 200-300元/天）
    ...
```

也支持技能类查询：`要求 YOLO 或计算机视觉的岗位有哪些？`、`有没有大模型微调相关的岗位？`

## 架构

```
                     ┌──────────────────────────────┐
   用户提问  ───────► │  FastAPI 服务 (:8020)         │
                     └───────────────┬──────────────┘
                                     │
                     ┌───────────────▼──────────────┐
                     │  混合检索 HybridRetriever     │
                     │  ┌─────────┐  ┌────────────┐ │
                     │  │  BM25   │  │  向量检索   │ │
                     │  │ 关键词路 │  │  语义路     │ │
                     │  └────┬────┘  └─────┬──────┘ │
                     │       └── RRF 融合 ──┘       │
                     └───────────────┬──────────────┘
                                     │ Top-K 岗位
                     ┌───────────────▼──────────────┐
                     │  Generator（本地 Qwen2-1.5B） │
                     │  拼 Prompt → 生成回答         │
                     └──────────────────────────────┘
```

| 层 | 实现 | 说明 |
|---|---|---|
| 服务 | FastAPI + uvicorn | 5 个端点，Pydantic 校验参数 |
| 关键词检索 | **自写 BM25**（k1=1.5, b=0.75）| 中文按 bigram 切，英文按词；零额外依赖 |
| 语义检索 | Qwen2-1.5B + mean pooling | 1536 维，归一化后 numpy 余弦 |
| 融合 | **RRF**（k=60）| 只看排名，免疫两路分数量纲差异 |
| 生成 | Qwen2-1.5B（CPU 推理）| 带 prompt 适配与输出清洗 |

## 快速开始

```bash
# 1) 装依赖（建议用虚拟环境）
python -m venv .venv
.venv\Scripts\activate            # Windows
pip install -r requirements.txt

# 2) 准备语料（把岗位数据合并成 data/jobs.jsonl）
python build_corpus.py

# 3) 启动服务
python server.py
# 打开 http://127.0.0.1:8020
# 首次点页面上的「构建/重建向量索引」（会加载模型，CPU 上 1~2 分钟）
```

**模型**：默认读本地 `F:\qwen_1.5b_local`（Qwen2-1.5B-Instruct）。
换路径改 `embedder.py` / `generator.py` 里的 `DEFAULT_MODEL_DIR`，或改用在线 API。

**接口**：

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/` | Web 界面 |
| GET | `/api/health` | 健康检查 + 索引/模型状态 |
| POST | `/api/index?force=true` | 构建/重建向量索引 |
| POST | `/api/query` | 提问（`{question, top_k, use_llm, temperature}`）|
| GET | `/api/docs?q=&offset=&limit=` | 列出/搜索语料里的岗位 |

**设计细节**：模型**懒加载**（启动服务不加载模型，避免起不来）；
**BM25 永远可用** —— 即使向量索引没建、模型没加载，关键词检索照样能答，
接口用 `retrieval_mode` 字段告诉调用方当前是哪一种。

## 踩坑记录（本项目最有价值的部分）

### 坑 1：我的纯向量检索是坏的 —— 而且不报错

我最初的方案是标准的"向量检索 + 大模型生成"。**实测效果不可接受**：

| 检索策略 | Top-5 命中 | 分数区分度 |
|---|---|---|
| 纯向量（原始）| 12/30 | **0.010** |
| 纯向量 + 去主成分 | 13/30 | 0.089 |
| **BM25（关键词路）** | — | **1.0 ~ 12.15** |

**区分度 0.010 意味着什么**：所有候选文档的分数挤在 0.87~0.94 之间，
排序基本等于随机 —— **但程序不会报错，只会安静地给出烂结果。**

**根因**：我拿 **Qwen2-1.5B 这个基座语言模型当 embedding 模型用**，导致**表示各向异性** ——
所有文本的向量都挤在一个窄锥里。实测证据：

```
"测试句子一"  与  "完全不同的另一句话"  的余弦相似度 = 0.884
```

**两句毫不相关的文本，相似度 0.884** —— 而真正相关的内容可能只有 0.86。
**区分度是负的。**

> 这个坑不看实测数据是发现不了的。它也提醒我一件事：
> **基座语言模型 ≠ embedding 模型**，做检索要用专门训练的（如 bge 系列）。

### 坑 2：向量归一化的静默 bug

`VectorIndex` 最初假设"传入的向量已归一化"，但构造时没归一化 →
`vectors @ q` 算的是**内积而不是余弦相似度** → 模长大的向量占优，**排序静默出错**。

自测时发现（查询应该命中"文档3"，结果"文档6"排第一）。
修法：**构造时就按行归一化**，并加了维度校验。

### 坑 3：小模型（1.5B）的 Prompt 适配 —— 四轮迭代

Qwen2-1.5B 的指令遵循能力很弱，同一个任务我试了四种写法：

| 版本 | 写法 | 模型表现 |
|---|---|---|
| 一版 | 多条规则 + 强制标注 `[n]` | **只输出 `[1]` 就停** |
| 二版 | 极简一句指令 | 答对了，但**只回一个岗位名**，太短 |
| 三版 | 给完整「问/答」示例（few-shot）| **把示例原样复读出来** |
| 四版 | 格式要求 + "没有内容就说没有" | **一律回答"没有找到相关岗位"** |
| **当前** | **只留一个明确动作**："列出相关岗位，写明名称/公司/地点/要求" | ✅ 正常 |

**结论**：对小模型，"给规则"和"给示例"都不如**给一个无条件的明确动作**。
第四版那句"没有内容就说没有"本意是抑制幻觉，实际是**给了模型偷懒的出口** ——
它会直接选最好答的分支。

另外加了**输出清洗**（`clean_answer`）：去掉模型复读的「问：」「答：」「【回答】」结构标记。

### 坑 4：CPU 推理慢

1.5B 在 CPU 上生成，上下文 700 字时单次要 **40~95 秒**。优化：

| 手段 | 效果 |
|---|---|
| 上下文截断到 320 字 | 关键信息都在开头，损失小 |
| `max_new_tokens` 512 → 200 | 答案本质是"列出岗位"，不需要长文 |
| 加 `StoppingCriteria` 检测重复输出 | 避免模型复读白烧时间 |

优化后降到 **15~60 秒**。**这是纯 CPU 的硬限制**，有 GPU 会快一个数量级。

## 目录结构

```
.
├── server.py               FastAPI 服务（HTTP 接口 + 静态页）
├── hybrid.py               混合检索（BM25 + 向量 + RRF 融合）

├── static/index.html       Web 界面
└── data/
    ├── jobs.sample.jsonl   语料样例（格式说明）
    └── resume.txt          简历纯文本（样例）
```

## 已知限制（如实记录）

| 限制 | 说明 | 改进方向 |
|---|---|---|
| **embedding 用的是基座模型** | 语义路质量差（坑 1），实际主要靠 BM25 | 换 **bge-small-zh** 等专用 embedding 模型 |
| **没做 rerank** | 只做了召回 + 融合，缺精排环节 | 召回后加 cross-encoder 精排 |
| **语料只有 74 篇，仅 22 篇有完整 JD** | 纯标题的文档对技能类查询匹配不上 | 补全 JD |
| **生成质量受模型规模限制** | 1.5B 有时输出重复、过于简略 | 换 7B 或调 API |
| **CPU 推理慢** | 15~60 秒/次 | 用 GPU |
| **不支持多轮对话** | 每次提问独立，不记得上文 | 加对话历史管理 |
| **检索评估较粗糙** | 只看 Top-5 是否包含期望关键词，未算 nDCG/MRR | 人工标注相关性后算标准指标 |

## 技术栈

| 层 | 用了什么 | 为什么 |
|---|---|---|
| Web 框架 | FastAPI + uvicorn | 轻量、异步、自带 API 文档，且岗位 JD 常要求"API 设计" |
| 关键词检索 | 自写 BM25 | 想搞懂机制而非调库；语料小，numpy 足够快 |
| 融合 | RRF | 免疫 BM25 与余弦相似度的量纲差异 |
| Embedding | Qwen2-1.5B（transformers）| 本地已有模型，零成本 |
| 生成 | Qwen2-1.5B | 同上 |
| 前端 | 原生 HTML/JS | 不需要构建工具 |
